# ADR 002 — Raspberry Pi gateway egress through Cloudflare WARP

Status: accepted (2026-11-05).

## Context
The `gateway` profile of `veil` sends all sandbox traffic to one allowlisted HTTP proxy on a Raspberry Pi 3B (`server.local`, Ubuntu 24.04 aarch64, Wi-Fi only). The goal is to hide the home IP from CLI vendors at no cost. The first version left through Tor, with a new circuit every 30 minutes. In every test, OpenCode's free models answered "Free usage limit reached" from Tor exits, so no end-to-end task completed. Circumventing that quota is out of scope.

## Decision
Replace Tor with Cloudflare WARP. Tor and WARP never share the same flow.

- Privoxy (port 8118, clients `192.168.0.0/24`) allows only `.opencode.ai:443` and forwards to wireproxy at `10.0.89.4:1080` on an internal Docker network.
- wireproxy is built from pinned sources (wgcf v2.3.1, wireproxy v1.1.3, golang.org/x/net v0.62.0) and holds the WireGuard tunnel to `162.159.192.1:2408`.
- `warp-init` registers the WARP device on first start. The account lives only in the `warp-data` volume.
- DNS is resolved by wireproxy over TCP inside the tunnel (`1.1.1.1`, `1.0.0.1`). UDP DNS through the tunnel failed often; over TCP 90 of 90 rounds succeeded, worst case 1.26 s.
- A watchdog runs `tunnel-check` (name resolution plus a TCP connection through SOCKS) every 10 s and restarts wireproxy after three failures. Packet captures showed that one UDP flow can be blocked upstream of the Pi while a new source port works at once. Two forced failures recovered in about 67 s and 77 s.
- Privoxy is published on all interfaces and reached as `server.local:8118`. After a power loss the Pi received a different DHCP address, and the old bind to `192.168.0.11` kept the gateway down.

## Evidence (2026-11-05, 00:47 UTC)
OpenCode v2.1.4 (`linux/arm64`) ran inside `veil run --profile gateway --home ~/vh` in a `debian:12.12-slim` container on the Mac, whose firewall dropped all output except TCP to the gateway. Direct access failed (`Could not resolve host: opencode.ai`). Through the gateway, OpenCode with `opencode/deepseek-v4.1-flash-free` added `subtrai(a, b)` to a test `calc.py`, and `veil` exited 0. All 219 packets left as TCP to port 8118, and no IPv4 packet was dropped. OpenCode state stayed in the dedicated home. On the Pi, wireproxy resolved only `opencode.ai` and `models.opencode.ai`. A trace through the tunnel showed `warp=on`, `colo=GRU`, and a Cloudflare exit address different from the home IP.

## Consequences
- The vendor sees a Cloudflare address shared with other WARP users, not the home IP. Cloudflare sees the home IP and the traffic metadata.
- There is no IP rotation. The exit address stayed the same within a tunnel; it changed after the first of three restarts and then stayed the same. Accounts, prompts and code can still link sessions.
- `veil` still runs only on Linux. On macOS it needs a Linux VM or container; the test used Docker Desktop.
- Not tested yet: first start with an empty `warp-data` volume, and `server.local` resolution on Linux hosts without mDNS.
